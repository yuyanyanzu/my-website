## 调用 #1 — 2026-10-05（Day 12 主任务）

**调用方式**：我对 AI 说「调用 filter-check 检查筛选交互」，AI 按 SKILL.md 的 description 匹配到本 Skill 并执行。

**执行命令**：

```bash

  node skill/filter-check/check-filter.cjs --browser
```

**本次发现的问题（这是 Skill 的价值所在）**：

1. **「无结果」这一路点不到** —— 静态检查发现标签栏只列出数据里存在的标签，8 篇笔记的 7 个标签每个都至少有 1 篇，所以点任意标签都筛不出空结果。AC-7 的空状态在正常操作下**无法触达**。
   - 修法：给 `app.js` 加 `?tag=标签名` 入口，可直接以某筛选状态打开页面。
2. **两种空状态文案存在混用风险** —— 「全站没笔记」和「筛选没结果」是两种不同情况，改动时容易合并成一句。
   - 修法：`renderNotes()` 里显式用 `activeTag !== "全部"` 区分，并在代码注释里写明为什么不能合并。
3. **被筛选的标签不在栏里** —— 从 `?tag=` 进来时，若该标签在数据里不存在，标签栏里没有任何按钮是选中态，用户不知道自己在看什么筛选。
   - 修法：`buildTagBar()` 里把当前 `activeTag` 补进标签列表并高亮；顺带给每个标签加篇数 tooltip，点之前就知道会不会是空的。
4. **检查脚本自身的 bug** —— 浏览器检查是 async，但没 `await` 就打印总结，导致「浏览器实测」标题下面空无一物。
   - 修法：包一层 `main()` 并在其中 `await runBrowserChecks()`。

**修复后结论**（30 项全通过）：

[通过] 当前筛选标签即使无笔记也会出现在标签栏并高亮
[通过] 情况1 有结果：点「前端」后卡片数减少：2 / 8
[通过] 情况1 剩下的卡片都含该标签
[通过] 筛选后通知条播报结果：已筛选标签「前端」，共 2 篇
[通过] 情况2 无结果：显示筛选空状态文案：标签「不存在的标签」下还没有笔记，点「全部」返回完整列表。

## 调用 #2 — 2026-10-05（收尾复跑，验证可重复）

**为什么要再跑一次**：提交前想确认「30 项全通过」不是一次性运气，而是可重复的结论。

**本次发现的问题（第 5 个）**：

5. **脚本不自带服务，重跑会假失败** —— 第一次复跑时 8080 上没有服务，puppeteer 卡 8 秒后抛
   `Waiting for selector ".note-card" failed`。这个报错**指向 CSS 选择器，实际是端口没人服务**，
   极具误导性——当时第一反应是去查 `components.js` 的卡片渲染，而代码其实没动过。
   - 修法：给 `check-filter.cjs` 加 `ensureServer()`，`--browser` 模式先探测 8080；
     没服务就自己起一个静态服务（带目录穿越防护），跑完在 `finally` 里关掉。
   - 复跑输出会出现一行「（8080 无服务，已自动启动本地静态服务）」确认是它自己起的。

**复跑结论**（30 项全通过，与调用 #1 一致）：

```
（8080 无服务，已自动启动本地静态服务）
[通过] 初始列表渲染 -> 8 篇
[通过] 情况1 有结果：点「前端」后卡片数减少 -> 2 / 8
[通过] 情况2 无结果：显示筛选空状态文案
[通过] 情况2 不是白屏（页面仍有可读内容） -> 292 字符
[通过] 情况3 清空恢复：点「全部」回到完整列表 -> 2 -> 8 / 8
[通过] 可访问性：回车键能触发筛选 -> 3 / 8
[通过] 全程无 JS 报错
=== 结论：通过 30 项，失败 0 项，提示 0 项 ===
```

**这次复跑的意义**：Skill 不只是"能跑一次"，而是"换台机器、隔几天再跑，结论一样"。

## 调用 #3 — 2026-10-07（隔两天再跑，验证结论稳定）

**为什么要再跑一次**：距上次已过两天，确认结论没有随时间或环境漂移。

**本次结果**：**30 项全通过**，与调用 #1、#2 完全一致。8080 无服务时脚本照例自己起了服务。

**本次发现的问题（第 6 个）**：

6. **诊断信息指向了错误的方向** —— 排查过程中遇到一次浏览器检查失败，报的是
   `Waiting for selector ".note-card" failed`。这个说法让人以为卡片渲染坏了、
   要去改 `components.js`；实际根因是 `index.html` 通过 **CDN** 引的 `marked.js`
   加载不到，而 `components.js:28` 的 `marked.parse()` 没有兜底，于是整张列表都渲染不出来
   ——**筛选逻辑本身根本没问题**。诊断指错方向，比没有诊断更浪费时间。
   - 修法：`check-filter.cjs` 在等不到 `.note-card` 时不再抛裸超时，
     改为沿渲染链逐环排查（`typeof marked` / `MOCK_NOTES` / `renderNotes`），
     直接给出「断在哪一环」的结论。
   - 验证：用一个临时脚本**掐断 marked.js 的请求**（模拟 CDN 不可达），确认诊断准确输出
     「marked 未加载」，而不是误报成卡片问题。验证后临时脚本已删除。

**另一个值得记住的现象**：即使断网，这次浏览器检查**仍然全通过**——因为 Edge 缓存了
`marked.js`。所以"这次跑通了"不能证明依赖不脆弱；要验证离线表现，必须清缓存或掐掉该请求。

**这次复跑的意义**：这是 Skill 第三次抓出问题，而且抓的是**它自己**的问题。
一个工具的报错信息如果把人引向错误的位置，那它就在帮倒忙。
